## 是正の対応表（Critical 1・Minor 3・Info 4）

### Critical-1: H 層 judgeHttp が byte 同一（旧==新）の allowlist 対象を PENDING のため無条件 FAIL

- **どう直したか**: `judgeHttp` を G 層 `compareTrees` と同じ
  **「差分があるときだけ allowlist を見る」** 構造へ変更した。
  - 旧 == 新（sha256 一致）→ allowlist に載っていても PENDING でも **PASS**
    （fix commit 前の正しい状態。§9.1 手順 6 の「AC3 が fix 前に green」を可能にする）。
    allowlist 対象である旨を notes へ記録する。
  - 旧 != 新 + allowlist 載り + 期待値採取済み → 新側を期待値と照合（不一致なら FAIL。現状どおり）
  - 旧 != 新 + allowlist 載り + PENDING → **FAIL**（期待値が無く判定不能。現状どおり）
  - 旧 != 新 + allowlist 外 → **FAIL**（現状どおり）
  - **PENDING を素通しする緩和ではない**。byte 不一致に対する fail-closed は全面的に維持。
- **自己テスト**: 委任指定の 4 ケースを `judge-11`〜`judge-14` として追加。
  既存 `judge-4`（採取済み一致→PASS）・`judge-5`（採取済み不一致→FAIL）はそのまま残存。
  `judge-6` の入力を旧==新から旧!=新へ修正（レビュー 1-4 が「この自己テストの期待値自体が
  設計 §9.1 手順 6 と矛盾」と明示した箇所。文言「PENDING のまま検査に使われたら FAIL
  （旧 != 新のとき）」に修正）。G 層にも同観点 `git-11`（blob 同一 + PENDING → PASS）を追加。
- **実証**: レビューと同じ再現条件（shizuoka.html を old==new・実 allowlist の PENDING で
  judgeHttp へ直接入力）で是正前 `fail / exit 2` → 是正後 `pass / exit 0` を実測。
  逆方向の fail-closed 維持も実測（旧!=新+PENDING → `fail / exit 2`・
  allowlist 外 byte 不一致 → `fail / exit 2`）。

## 設計内部矛盾について（レビュー観点 4 の指摘の行き先）

レビューは「§4.6-H の shizuoka PASS 条件（新側==fix 後期待値）は fix commit 後しか成立
しない一方、§9.1 手順 6 は fix 前に AC3 green を要求する。両立しない」と設計の内部矛盾を

allowlist が関与しないことと矛盾しない——「差分があるときだけ allowlist を見る」構造は
この読みをそのまま実装に落としたものである。設計書側への文面明示（§4.6-H に
